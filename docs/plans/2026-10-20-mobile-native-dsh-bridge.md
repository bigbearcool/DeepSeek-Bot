# 手机原生远程控制 dsh（经桥接插件）

- 日期：2026-10-20（同日更新：拍板 MVP = Android + 桥接插件；鸿蒙二期；工具跟 Bot 原权限）
- 状态：方案（未开工——等大熊/园长说开干再写代码）
- 读者：大熊、传杰、园长
- 相关：现有 [桌面应用方案](2026-10-16-desktop-app.md)、ds-bot 的 `/api/bot` 与 `/api/bot/feed`（SSE）

---

## 结论（先看这段）

1. **MVP = Android 原生 App + `dsh-mobile-bridge` 插件。** 不做壳包网页；模型与工具仍在 NAS（或家里机器）上的 **dsh + ds-bot** 里跑。
2. **鸿蒙先不跟。** 鸿蒙机用**卓易通**装安卓包即可；**鸿蒙原生 App 放二期。**
3. **桥接插件**专门给手机当远程控制面：配对鉴权、列 Bot、看历史、发消息、流式推送。**不替代 ds-bot 的桌面/网页 UI。**
4. **App 不跑模型、不本地 Agent。** 手机只发指令、收流式结果；回合与工具仍走现有 dsh Session 与 ds-bot。
5. **MVP 范围收窄**：配对登录 → 列 Bot → 看历史 → 发消息 → 看流式。工具继续走 ds-bot/dsh **原有权限**——**不要**在手机端另开远控/命令入口，也**不要**为了「安全」去关掉 Bot 本身已有的工具。MeshCentral 等只是「App 不做专用面板」，**不是**关园长运维或关 Bot 能力。
6. **外网经现有 Lucky / Mesh 网关进内网**；插件只听本机或内网；鉴权用「设备登记 → 换短期令牌」（对齐小圣侧栏：设备长期、令牌短命、可吊销）。
7. **粗估**：MVP 约 3–5 人周（桥接插件 + Android）；二期（鸿蒙原生、审批、推送、群聊等）另计。当前**只改文档，等开干指令后再写代码。**

## 1. 三层结构

```
┌──────────────────────────────┐
│  Android 原生 App（MVP）        │  ← 只做控制面与展示
│  （鸿蒙机：卓易通装安卓包）      │
└──────────────┬───────────────┘
               │ HTTPS（经 Lucky/Mesh 等到家里）
               │ 短期令牌
┌──────────────▼───────────────┐
│  dsh-mobile-bridge（新插件）   │  ← 鉴权 + 会话/消息 API + 流式
│  （跑在同一套 dsh 进程里）      │
└──────────────┬───────────────┘
               │ 进程内调用 / 复用现有通道
┌──────────────▼───────────────┐
│  dsh 引擎 + ds-bot             │  ← 已有：Bot、Session、工具、审批、feed
└──────────────────────────────┘
```

| 层 | 职责 | 不做什么 |
|---|---|---|
| **Android App（MVP）** | 配对登录、列 Bot、历史、发消息、流式展示 | 不跑模型、不壳包 WebView 当主界面、不做远控/命令专用面板 |
| **dsh-mobile-bridge** | 设备鉴权、把手机请求接到 ds-bot/dsh、把 feed/流式转给手机 | 不重做 Bot 团队 UI、不存第二份对话真相、不削弱 Bot 已有工具 |
| **dsh + ds-bot** | 唯一真相：Bot、Session、消息、工具、权限、密钥 | 不直接对公网裸奔；外网入口交给现有网关 |

**为何是独立插件而不是改 ds-bot？**

- ds-bot 已有给浏览器用的 `POST /api/bot` 和 `GET /api/bot/feed`（SSE），面向的是「已在 dsh Web/桌面登录态里的本机窗口」。
- 手机需要：**设备级鉴权、短令牌、跨公网、精简字段、可版本化的移动协议**。这些塞进 ds-bot 会和桌面 UI 纠缠。
- 桥接插件**调用** ds-bot 已有能力；桌面用户不受影响；卸掉插件即关掉远程面。

**平台拍板**

| 阶段 | 客户端 |
|---|---|
| **MVP** | **Android 原生** + `dsh-mobile-bridge` |
| 鸿蒙机（过渡） | 用**卓易通**安装上述安卓包 |
| **二期** | 鸿蒙原生 App；视需要再补 iOS |

不做「PWA / Capacitor 包网页」作为目标形态；WebView 仅允许调试协议，不进正式交付。

## 2. 桥接插件对外接口（草案）

基址示例：`https://<家里入口>/mobile-bridge/v1`（插件注册到 dsh HTTP；网关反代时只暴露这一前缀）。

### 2.1 鉴权（对齐小圣侧栏思路）

| 步骤 | 行为 |
|---|---|
| 配对 | 在 **dsh/ds-bot 本机界面** 显示一次性配对码或二维码（短时有效）；手机扫码/输入 → 登记「设备 ID + 公钥/设备密钥」 |
| 换票 | 设备证明身份 → **短期访问令牌**（建议 15–60 分钟）+ 可吊销的刷新令牌 |
| 使用 | `Authorization: Bearer <access>`；过期只刷新，不重跑配对 |
| 吊销 | 本机「已配对设备」列表一键踢掉 |

原则：长期凭证不出公网日志；不复用 dsh 网页 Cookie 当远程方案。

### 2.2 会话与消息（MVP 必做）

| 能力 | 方法（示意） | 说明 |
|---|---|---|
| 团队 / Bot 列表 | `GET /team` | 列 Bot；MVP 可不含群聊 |
| 会话历史 | `GET /chats/{botId}/messages` | 分页；字段精简；不回传密钥 |
| 发送 | `POST /chats/{botId}/messages` | 用户文本；附件二期 |
| 流式 | `GET /stream` 或过滤后的 feed | 见下节 |

实现上优先 **复用 ds-bot 已有语义**（botId、Session、exchangeTurns），避免手机另造会话 ID。

### 2.3 流式

- **推荐 SSE**（与现有 `GET /api/bot/feed` 同族：`revision` / `live` / `message` / `stream`）。
- 桥接可代理/过滤 feed，或提供仅当前 Bot 的 text-delta 精简流。
- WebSocket 备选；事件语义与 SSE 对齐。
- 断线：重拉历史 + 再订流；慢客户端限队列（可借鉴 ds-bot feed）。

### 2.4 Bot 切换

- 列表来自团队状态；App 选中的 `botId` 决定订阅与发送目标。
- 新建 Bot、改预设仍以桌面/网页为准（二期再考虑只读展示）。

### 2.5 工具与权限（拍板后的口径）

**核心一句：手机不另开工具面，也不关 Bot 原有工具。**

| 说法 | 对不对 |
|---|---|
| Bot 在 dsh 里该有的读文件、命令、浏览器等，继续按 **ds-bot / dsh 原有权限与审批** 跑 | ✅ |
| 为了「手机安全」在桥接层关掉 Bot 工具、或改瘦 Bot 权限预设 | ❌ 不要 |
| 在 Android App 里做 MeshCentral / 远控 / 终端专用入口 | ❌ MVP 不做 |
| 园长用 Mesh 运维 NAS、Bot 侧已接的能力 | ✅ 与 App 无关，不因本方案关闭 |

桥接插件 **不得** 提供「代用户自动点批准」的后门；也 **不得** 为远程场景单独抬权。用户在手机上发一句话之后，Bot 用工具仍走桌上同一套规则（含该批准的批准）。

## 3. 边界（写清楚避免以后扯皮）

| 可以 | 不可以 |
|---|---|
| 手机远程看 Bot 说话、发消息、看流式 | App 内嵌模型或离线 Agent |
| 插件把移动协议接到 ds-bot/dsh | 插件重做 ds-bot UI / 第二份 state.json |
| 经网关只暴露桥接前缀 | 把整个 dsh Web 管理面裸露公网 |
| 设备级吊销与短令牌 | 长期 API Key 写死在 App 里 |
| 工具跟 Bot 原权限走 | 手机另开远控/命令面板；或为安全关掉 Bot 工具 |
| 鸿蒙机卓易通装安卓包 | MVP 做鸿蒙原生 |

与桌面应用方案一致：**引擎用 dsh，不另写 Agent 运行时。** 手机只是多一个客户端。

## 4. 外网与安全（点到为止，运维归园长）

- **入口**：Lucky / Mesh 等到内网 dsh；桥接绑定 `127.0.0.1` 或内网，**不直接对公网听端口**。
- **TLS**：外网段由网关终止证书。
- **路径最小化**：只反代 `/mobile-bridge/`（或约定前缀）。
- **速率**：配对码、刷新令牌、按设备限流。
- **审计**：记设备 / 时间 / 目标 Bot；避免把消息全文打进不必要日志。

园长侧：网关规则、证书、dsh 常驻与备份——本方案不展开 NAS 步骤。

## 5. MVP vs 二期

### MVP（已拍板）

- **`dsh-mobile-bridge`**：配对、短令牌、列 Bot、历史分页、发送文本、SSE 流式、踢设备；可整灯关闭远程面。
- **Android 原生 App**：配对登录、Bot 列表、聊天页、流式、基础错误与重连。
- **不做**：壳包网页、鸿蒙原生、手机审批面板、群聊、远控/命令专用入口、为安全关 Bot 工具。

### 二期

- **鸿蒙原生 App**；视需要 iOS。
- 推送通知；手机上点审批；群聊；图片/文件；停转。
- 只读展示 preset / 用量等。

## 7. 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 鉴权做错 | 令牌过长、日志泄漏、设备被盗 | 短令牌、可吊销、本机设备列表 |
| 误暴露整个 Web UI | 攻击面过大 | 网关只反代桥接前缀 |
| feed 形状随升级变化 | 手机流式断裂 | 桥接适配层 + 最小事件集 |
| 误解「关工具」 | 误伤园长/Bot 能力 | 文档写清：只不做 App 专用面板 |
| 当成壳包网页 | 违背拍板 | 验收以 Android 原生界面为准 |
| 未开干先铺脚手架 | 方向再变成本高 | **等大熊/园长说开干再写代码** |

## 8. 建议的下一步

**当前：只维护本文档，不写代码、不搭脚手架。**

若大熊/园长说可以开干，**建议第一步做桥接插件骨架**（而不是先建 Android 工程）：

1. 在开发用 dsh profile 里挂上空的 `dsh-mobile-bridge`：健康检查、配对码占位、`GET /team` 先返回固定/读 ds-bot 的只读快照、SSE 能把一条测试事件推到 `curl`。
2. 理由：协议与鉴权是两端共用的契约；插件先通，Android 只消费稳定 API，返工更少。网关也可先对插件前缀做反代联调。
3. 插件骨架可联调后，再起 Android 工程：配对页 → 列表 → 聊天 + 流式。

开干前仍建议园长点头：网关能否只暴露桥接路径前缀。

## 附录：与现状的对齐（只读结论）

- ds-bot 已是标准 dsh 插件；桌面方案已强调「引擎用 dsh、界面可独立」。
- 浏览器侧已有 `POST /api/bot` 与 `GET /api/bot/feed`（SSE）。桥接应 **复用语义 + 加设备鉴权**，而不是让 App 直连未鉴权的桌面同源接口。
- Bot 权限与工具模型已存在；远程面是**多一个说话入口**，不是平行权限系统，也不是关工具的开关。
